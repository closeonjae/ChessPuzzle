# design-review

> **출처**: [garrytan/gstack](https://github.com/garrytan/gstack)의 `design-review` + `plan-design-review` (MIT).
> `DESIGN_SKILLS.md`의 [nexu-io/open-design](https://github.com/nexu-io/open-design)에도 같은 항목이 있으나 그쪽은 카탈로그 스텁이라 실제 절차가 없고, upstream이 원본이다.
>
> **원본에서 덜어낸 것과 이유**
> - gstack 전용 배관(업데이트 체크, 텔레메트리, gbrain 동기화, 세션 파일) — 이 저장소에 gstack이 없어 동작하지 않고, 외부에서 가져온 지시가 셸을 실행하게 두지 않는다.
> - 브라우저 구동(`$B screenshot`, localhost 포트 탐지, 반응형 브레이크포인트) — 이 앱은 웹이 아니다. 아래 "화면을 보는 법"으로 대체했다.
> - 랜딩페이지 규칙(히어로, 캐러셀, 풀블리드, 브랜드 우선순위) — 480×480 원형 워치 앱에 해당하지 않는다. "원형 워치 하드 룰"로 대체했다.
>
> **그대로 가져온 것**: 감사 단계 구성, 비평 문법, 0~10 평가법, 근거 규칙, AI 슬롭 탐지, Quick Wins.

## 언제 쓰나

이미 화면에 그려지는 것을 평가할 때. 구현 전 계획 검토가 아니다.

쓰지 않는 경우:
- 조작 가능성/휴리스틱 평가가 목적이면 내장 `usability` 스킬이 더 정확하다. 이 스킬은 **보이는 것**(시각적 완성도·의도·일관성)을 본다.
- 버그를 찾는 것이 목적이면 `/code-review`.

## 화면을 보는 법 (이 저장소의 실제 경로)

**소스를 읽고 평가하지 마라.** 렌더링된 화면을 본다. 코드는 지적한 것을 고칠 때만 연다.

```bash
# 빌드
JAVA_HOME="/c/Program Files/Android/Android Studio/jbr" ./gradlew.bat :app:assembleDebug --offline

# 에뮬레이터(로그인 불필요) — 캔 데이터로 전 상태를 재현할 수 있다
adb -e install -r app/build/outputs/apk/debug/app-debug.apk
adb -e shell "am start -a com.closeonjae.chesspuzzle.PREVIEW_PUZZLE"     # 퍼즐 화면
adb -e shell "am start -a com.closeonjae.chesspuzzle.PREVIEW_OPENING"    # 모드 선택 → 오프닝 화면

# 실물 워치(무선 디버깅) — 실제 Lichess 데이터가 필요할 때만
adb mdns services | grep RFAYA          # 유휴 시 끊기고 포트가 매번 바뀐다
adb connect <ip>:<port>

# 스크린샷 (PowerShell 리다이렉션은 바이너리를 깨뜨린다 — 기기에 쓰고 pull)
adb -s <dev> shell "screencap -p /sdcard/s.png" && adb -s <dev> pull /sdcard/s.png ./s.png
```

찍은 스크린샷은 **반드시 Read 도구로 열어 사용자에게 보여준다.** 안 그러면 근거가 보이지 않는다.

`adb install -r`이 새 APK를 반영하지 않은 적이 있다. 화면이 안 바뀌면 기기 APK 해시를 로컬과 비교하고, 다르면 uninstall 후 재설치한다.

## Phase 1 — 첫인상

분석하기 전에 반응부터 적는다. 이 스킬에서 가장 디자이너다운 산출물이다.

1. 각 화면의 기본 상태를 한 장씩 찍는다.
2. 아래 형식으로 쓴다:
   - "이 화면은 **[무엇]**을 말한다." (한눈에 전달되는 것 — 유능함? 혼란? 성의 없음?)
   - "가장 먼저 눈이 가는 곳은 **[어디]**다." (의도한 곳인가?)
   - "**[무엇]**처럼 느껴진다." (톤)
3. 화면의 목적이 하나로 읽히는가? 안 읽히면 그 자체가 첫 지적이다.

## Phase 2 — 디자인 시스템 추출

스크린샷에서 실제로 쓰이는 색·크기·간격·아이콘을 뽑아낸 뒤, **`DESIGN.md`와 대조**한다. 이 저장소는 DESIGN.md가 단일 소스이고 `ui/theme/`가 그 전사본이다.

- 문서에 없는 값이 화면에 있는가? (표류)
- 문서에는 있는데 화면에 없는가? (미구현)
- 같은 역할에 두 값이 쓰이는가? (예: 아이콘이 이모지와 벡터로 섞임 — 이 앱에서 실제로 있었던 일)

어긋난 것은 "코드가 틀렸다"가 아니라 **어느 쪽이 옳은지**까지 판단해 적는다.

## Phase 3 — 화면별 감사

화면마다, 상태마다 스크린샷을 놓고 아래를 본다.

- **위계**: 가장 중요한 것이 가장 크고 위에 있는가? 다 소리치면 아무것도 안 들린다.
- **여백**: 간격이 관계를 말하는가, 아니면 전부 균일해서 아무 말도 안 하는가?
- **정렬**: 광학적으로 맞는가? 기하학적 중앙이 시각적 중앙이 아닌 경우가 있다(숫자·아이콘).
- **잘림**: 긴 텍스트, 큰 숫자, 긴 이름에서 무엇이 잘리는가? 실제 최댓값으로 확인한다.
- **터치**: 누를 수 있어 보이는가? 실제 타깃이 48dp 이상인가?
- **대비**: 아래 하드 룰의 수치로 **실제 합성된 색**을 계산한다(반투명 오버레이는 밑색과 섞인다).

## Phase 4 — 상태 검토

기본 상태만 보면 안 된다. `DESIGN.md`가 열거한 상태를 전부 재현해 찍는다.

로딩(첫 진입) · 갱신 대기 · 빈 상태 · 오류 · 긴 텍스트 · 비활성 컨트롤 · 조작 중(선택·입력).

각각에 대해: **무엇을 기다리는지 밝히는가? 오류가 사실 진술과 구분되는가?**(예: "기록 없음"은 실패가 아니다) **되돌릴 수 있는가?**

## Phase 5 — 화면 간 일관성

이 앱의 규칙은 "같은 기능은 모든 화면에서 같은 자리"다. 퍼즐 화면과 오프닝 화면은 같은 골격(보드, 좌·우 반달 탭, 상단 텍스트, 하단)을 공유한다.

- 같은 슬롯이 화면마다 다른 성격의 동작을 하는가?
- 같은 의미를 다른 시각 언어로 말하는가?
- 한 화면에서 배운 것이 다른 화면에서 통하는가?

## Phase 6 — 보고

항목마다 **0~10점**을 매기고, **10점이 이 화면에서 무엇인지** 적는다. 점수만 적는 것은 쓸모가 없다.

| 항목 | 본다 |
|---|---|
| 첫인상 | 목적이 한눈에 읽히는가 |
| 위계와 여백 | 중요도 순서가 시각적으로 드러나는가 |
| 타이포 | 크기 단계가 의미를 갖는가, 잘림은 없는가 |
| 색과 대비 | 수치로 통과하는가, 색이 정보를 나르는가 |
| 상태 설계 | 로딩·빈·오류·긴 텍스트가 전부 설계되었는가 |
| 일관성 | 화면 간 같은 자리·같은 언어인가 |
| 슬롭 신호 | 아래 목록 |

마지막에 **Quick Wins 3~5개** — 각각 30분 안에 끝나면서 효과가 큰 것.

## 원형 워치 하드 룰

이 앱 고유의 기하·물리 제약. 위반은 취향 문제가 아니라 결함이다.

1. **원의 현(chord)**: 높이 y에 놓인 가로 요소가 쓸 수 있는 폭은 `2·√(r² − (r−y)²)`다. **"480px 안"이 곧 "화면 안"이 아니다** — 사각형 기준으로 맞춰도 원 위·아래에서는 잘린다. 이 프로젝트에서 세 번 물린 함정이다(하단 막대 2회, 상단 이름 1회).
2. **터치 타깃 48dp 이상.** 시각적 크기가 작아도 실제 영역은 확보한다.
3. **대비**: 본문 4.5:1, 도형·지시자 3:1. 반투명 오버레이는 **밑에 깔린 색과 합성한 결과**로 계산한다. 밝은 칸과 어두운 칸 양쪽에서 통과해야 한다.
4. **OLED 배경은 순검정.** 소비전력과 대비를 동시에 얻는다.
5. **화면마다 목적 하나**, 그 목적에 맞는 것이 가장 크고 위에.
6. **같은 기능은 같은 자리.** 화면이 바뀌어도 슬롯은 안 움직인다.
7. **회전 베젤 없음**(Galaxy Watch 8 비-Classic). 터치 스크롤이 기본이다.
8. **요청받지 않은 모션은 없다.**

## AI 슬롭 신호

대부분의 개발자는 자기 화면이 기계가 만든 것처럼 보이는지 판단하지 못한다. 이건 직설적으로 말해준다.

- 아무 앱에나 얹어도 되는 카드 스택 — 레이아웃 대신 카드로 때운 흔적
- 기본 폰트 스택에 기본 자간, 크기 단계가 의미 없이 두세 개
- 장식용 그림자·라운드가 모든 요소에 균일하게
- 전부 가운데 정렬
- 아이콘 출처가 섞임(이모지 + 벡터), 이모지는 색 지정이 안 먹어 톤이 깨진다
- 상태가 기본 하나뿐 — 로딩·빈·오류가 "나중에"로 남아 있음
- 값이 문서에 근거 없이 존재(왜 13dp인지 아무도 모름)

**리트머스**: 장식용 그림자와 라운드를 전부 걷어내도 고급스러운가? 그렇다면 구조가 좋은 것이고, 아니라면 장식이 구조를 대신하고 있었던 것이다.

## 비평 문법

의견이 아니라 구조로 쓴다.

- **"~가 보인다"** — 관찰. ("하단 막대가 오른쪽 끝에서 잘려 보인다")
- **"~일까"** — 질문. ("사용자가 이 숫자를 순위로 읽을까, 개수로 읽을까")
- **"~하면 어떨까"** — 제안. ("배지를 도착 칸이 아니라 출발 칸에 두면 어떨까")
- **"~라고 본다, 왜냐하면 ~"** — 근거 있는 판단.

## 규칙

1. **QA가 아니라 디자이너로 본다.** "동작하는가"가 아니라 "의도적으로 보이는가, 사용자를 존중하는가"를 본다.
2. **스크린샷이 근거다.** 모든 지적에 최소 한 장. 찍었으면 Read로 열어 보여준다.
3. **구체적으로.** "간격이 어색하다"가 아니라 "X를 Y로, 왜냐하면 Z".
4. **소스를 읽고 평가하지 않는다.** 렌더링된 화면을 본다.
5. **넓이보다 깊이.** 근거와 제안이 붙은 5~10개가, 막연한 20개보다 낫다.
6. **찾는 대로 적는다.** 몰아서 쓰지 않는다.
7. **측정 도구를 의심한다.** 잉크 무게중심은 시각적 중심이 아니고, 셀 중심 추정은 ±0.5px 흔들린다. 개선을 주장하기 전에 기준선(예: 원 피팅으로 구한 실제 중심)이 옳은지 먼저 확인한다.
8. **고치지는 않는다.** 이 스킬은 평가까지다. 고칠지는 사용자가 정한다.
